# sAiity 2.0 Speaker Labels Implementation Plan

> **For agentic workers:** Use the repository's test-first workflow and keep each task independently reviewable. Do not begin Windows implementation until the macOS diarization contract and the overlay spike have produced verified results.

**Goal:** Add honest, local speaker labels to saved and live transcripts on macOS, then use the stable transcript contract as the foundation for the Windows 2.0 port.

**Architecture:** Keep `Segment.turn` as the existing compatibility-preserving turn-boundary field and add an optional speaker identifier beside it. Diarization remains a native FluidAudio concern; sentence assembly, persistence, exports, viewer rendering, and speaker naming consume a small platform-neutral `SpeakerID` value. Old JSONL sessions decode with no speaker and remain exportable.

**Tech Stack:** Swift 6, Swift Testing, SwiftUI/AppKit, FluidAudio 0.15.5, SwiftPM, JSONL persistence, Sparkle-compatible release tooling.

## Global Constraints

- Keep all audio and diarization on-device; no server transcription.
- Preserve decoding of existing sessions that have no speaker field.
- Do not claim a speaker name unless the user assigns it or the mic channel is deterministically known as `Me`.
- Preserve the current sentence-order, translation, and export invariants.
- Keep macOS green before starting Windows work.
- Pin the diarizer model/runtime versions together and record the tested versions.
- Never ship a Windows overlay architecture before the click-through/backdrop spike has a measured result.
